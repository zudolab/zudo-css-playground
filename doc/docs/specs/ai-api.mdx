# AI API

The AI chat API enables pattern generation through a local Claude CLI integration. The system uses a **two-step deferred file writing** pattern: the chat endpoint generates content and returns it to the client, and a separate apply endpoint writes files to disk when the user confirms.

## Endpoints

### POST /api/ai-chat

Generates AI responses. For pattern creation, returns pending file content without writing to disk (prevents Astro HMR from reloading the page before the response reaches the client).

### POST /api/ai-chat-apply

Writes pending files to disk and updates the sidebar navigation. Called by the client when the user clicks "Apply & Reload".

Both routes are server-side rendered (`export const prerender = false`) and require the Node adapter.

## Request Format

### /api/ai-chat

```typescript
{
  message: string;          // Required. The user's request.
  history?: ChatMessage[];  // Optional. Previous conversation messages.
}

interface ChatMessage {
  role: "user" | "assistant";
  content: string;
}
```

### /api/ai-chat-apply

```typescript
{
  files: Record<string, string>;  // filename → file content
  sidebarEntry?: {
    slug: string;
    label: string;
    count: number;
  };
}
```

### Validation Rules

| Field           | Constraint                                                                                                                       |
| --------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| `message`       | Required, non-empty string, max 4000 characters                                                                                  |
| `history`       | Optional array, max 20 entries. Each entry must have valid `role` ("user" or "assistant") and `content` (string, max 4000 chars) |
| `files` (apply) | Required, must be an object. Only `.astro` filenames without `..` or `/` are accepted                                            |

## Response Format

### Pattern Creation (pending_files)

When the AI creates new patterns, the chat endpoint returns the file content without writing to disk:

```json
{
  "action": "pending_files",
  "pendingFiles": {
    "breadcrumbs.astro": "<full Astro page content>"
  },
  "sidebarEntry": {
    "slug": "breadcrumbs",
    "label": "Breadcrumbs",
    "count": 10
  },
  "files": ["breadcrumbs.astro"],
  "message": "Created 10 breadcrumb patterns!",
  "needsReload": true
}
```

The client stores the pending files in component state and displays a success message with an "Apply & Reload" button. When clicked, the client sends the pending files to `/api/ai-chat-apply`, which writes them to disk, then reloads the page.

### Chat Response

When the AI responds with text (no file creation):

```json
{
  "action": "chat",
  "message": "The token system uses CSS custom properties..."
}
```

### Apply Response

```json
{
  "ok": true,
  "files": ["breadcrumbs.astro"]
}
```

### Error Responses

```json
// 400 Bad Request
{ "error": "message required" }
{ "error": "message too long" }
{ "error": "Invalid JSON" }
{ "error": "files required" }

// 429 Too Many Requests
{ "error": "Another request is in progress. Please wait." }

// 500 Internal Server Error
{ "error": "Timeout after 480s" }
{ "error": "claude exited 1: <stderr output>" }
{ "error": "Spawn failed: <error message>" }
```

## System Prompt Overview

The AI receives a detailed system prompt that includes:

- Instructions to respond with structured JSON (not markdown)
- The exact Astro page template format
- The complete list of token variables with their values
- Rules for BEM-ish class naming
- The prohibition against arbitrary hex colors, pixel values, and HSL values
- Instructions for both pattern creation and general chat responses

The system prompt defines two response formats:

**Pattern creation** (`action: "create_patterns"`):

```json
{
  "action": "create_patterns",
  "category": "breadcrumbs",
  "label": "Breadcrumbs",
  "files": {
    "breadcrumbs.astro": "<full Astro page content>"
  },
  "sidebarEntry": {
    "slug": "breadcrumbs",
    "label": "Breadcrumbs",
    "count": 10
  },
  "message": "Created 10 breadcrumb patterns!"
}
```

**General chat** (`action: "chat"`):

```json
{
  "action": "chat",
  "message": "Your answer here"
}
```

## Deferred File Writing Flow

### Why Deferred?

In development, Astro's file watcher triggers hot module replacement (HMR) whenever files change on disk. If the AI endpoint wrote `.astro` files directly, the page would reload before the fetch response reached the client — destroying the chat modal state and preventing the user from seeing the result.

### Process Flow

1. **Parse and validate** the incoming request JSON
2. **Read context**: Check which pattern pages exist on disk and read the current `sidebar-nav.tsx`
3. **Build prompt**: Combine the system prompt, conversation history, existing page context, and the user's message
4. **Spawn Claude CLI**:
   ```bash
   claude -p --model haiku --max-budget-usd 0.50 --system-prompt "..." < prompt
   ```
5. **Parse response**: Strip any markdown code fences, parse as JSON (handled by `parseAiResponse()` in `src/lib/parse-ai-response.ts`)
6. **If `action: "create_patterns"`**:
   - Validate filenames (handled by `isValidAstroFilename()` in `src/lib/validate-astro-filename.ts`)
   - Return `{ action: "pending_files", pendingFiles: {...}, ... }` — files are NOT written yet
7. **Client shows success message** with "Apply & Reload" button
8. **User clicks "Apply & Reload"**:
   - Client sends pending files to `POST /api/ai-chat-apply`
   - Apply endpoint writes `.astro` files to `src/pages/`
   - Apply endpoint updates `sidebar-nav.tsx` via `updateSidebarNavContent()` in `src/lib/update-sidebar-nav.ts`
   - Client reloads the page

### File Safety

Both endpoints enforce strict file writing rules:

- Only `.astro` files are written (other extensions are silently skipped)
- Path traversal is blocked (`..` and `/` in filenames are rejected)
- All files are written to the `src/pages/` directory only
- Validation is handled by the shared `isValidAstroFilename()` function

## Shared Library Modules

The AI API logic is organized into shared, testable modules in `src/lib/`:

| Module                       | Purpose                                                    |
| ---------------------------- | ---------------------------------------------------------- |
| `parse-ai-response.ts`       | JSON parsing, code fence stripping, response routing       |
| `validate-astro-filename.ts` | `.astro` filename validation (no `..`, no `/`)             |
| `update-sidebar-nav.ts`      | Sidebar categories array manipulation (add/update entries) |

These modules are imported by both `ai-chat.ts` and `ai-chat-apply.ts`, eliminating code duplication.

## How sidebar-nav.tsx Is Auto-Updated

The `updateSidebarNavContent()` function modifies the sidebar categories:

```typescript
function updateSidebarNavContent(
  content: string,
  entry: { slug: string; label: string; count: number },
): string;
```

It handles multiple array formats:

- **Single-line empty array**: `const categories: ... [] = [];` → expands to multi-line with new entry
- **Multi-line array**: Inserts new entry before closing `];`
- **Existing category**: Updates the count via regex match

## Rate Limiting

The chat endpoint uses a simple in-memory `inFlight` flag:

- Only **1 concurrent request** is allowed
- Additional requests receive HTTP 429 with `"Another request is in progress. Please wait."`
- The flag is cleared in a `finally` block to ensure cleanup even on errors

This is a module-level variable, so it works within a single Node.js process. It does not persist across server restarts.

## Input Validation

| Check                                       | Behavior                              |
| ------------------------------------------- | ------------------------------------- |
| Missing or non-string `message`             | 400: "message required"               |
| `message` > 4000 chars                      | 400: "message too long"               |
| Invalid JSON body                           | 400: "Invalid JSON"                   |
| `history` items with invalid `role`         | Silently filtered out                 |
| `history` items with `content` > 4000 chars | Silently filtered out                 |
| `history` > 20 items                        | Truncated to last 20                  |
| Concurrent request                          | 429: "Another request is in progress" |

## Local Claude CLI Integration

The API spawns the `claude` CLI as a child process:

```typescript
const proc = spawn(
  "claude",
  [
    "-p",
    "--model",
    "haiku",
    "--max-budget-usd",
    "0.50",
    "--system-prompt",
    SYSTEM_PROMPT,
  ],
  { stdio: ["pipe", "pipe", "pipe"] },
);
```

### Configuration

| Parameter    | Value                       |
| ------------ | --------------------------- |
| Mode         | `-p` (pipe/non-interactive) |
| Model        | `haiku`                     |
| Budget limit | $0.50 per request           |
| Timeout      | 480 seconds                 |

### Error Handling

- **Timeout**: After 480s, the process is killed with `proc.kill()` and a "Timeout after 480s" error is returned
- **Non-zero exit code**: Returns the stderr output in the error message
- **Spawn failure**: Returns "Spawn failed" with the OS error
- **Invalid JSON response**: Falls back to returning the raw text as a chat message
